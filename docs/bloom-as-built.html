Bloom as built: what the system does today

A code-level account of how Bloom learning paths are generated, stored, shown and progressed. It describes, it does not recommend. Every statement cites a file so it can be checked.

01Executive summary

Bloom is a per-student, student-initiated space for short learning paths. A path is a title, a goal, an AI-written summary and an ordered list of 3, 5 or 7 tasks. Each task is typed learn, do or reflect. Confirmed

  • No API routes. Everything runs through Next.js server actions in apps/web/src/app/student/bloom/actions.ts that talk to Supabase (Postgres with row-level security). There are no REST endpoints, background jobs or queues.
  • Up to three AI functions, all in apps/web/src/lib/ai.ts. suggestBloomPaths returns 3 path ideas as JSON. planBloomPath returns a summary and tasks as JSON. askBloom returns a plain-text answer. All use Anthropic model claude-opus-5-5 at low effort, and prompts are hard-coded TypeScript strings.
  • What the AI is told about the student. Age group, current programme step name, week number, the project's area, title, problem and status, and up to 12 earlier path titles. Nothing else from the student's work, reflections, questions, mentor notes or course submissions is sent.
  • Progress is self-reported. A task moves through todo → doing → done when the student clicks. No evidence, check or approval is needed. When every task is done the path becomes completed; reopening a task sets it back to active.
  • One free-text field per task. bloom_tasks.reflection stores both "Add a note" and reflect-task answers. Questions to Bloom and the answers are kept in bloom_questions.
  • Others can watch. Mentors, parents and admins can read everything through RLS (can_view_student). Mentors and admins can leave one note per path. AI features need a parent's bloom_ai consent.
  • Not linked to the course. A path is tagged with the cohort and programme step it started in, but it has no link to the project row, programme activities or submissions.

03Bloom generation flow

There are two entry routes into the same createPath action.

Route A: "Suggest ideas", then "Start this path"

Two AI calls. The first returns 3 ideas, which are not saved. The second plans the chosen one. The card always submits depth=standard (5 tasks) and useAi=on.

Route B: "I have my own topic"

One AI call, or none if "Let Bloom plan" is unticked. The student supplies the title (required), goal (optional) and depth (3, 5 or 7 tasks).

User action

Route A: types an optional interest (max 300 characters) and clicks Suggest ideas, then Start this path on a card. Route B: fills the own-topic form and clicks Create path.

Frontend

StartPath in forms.tsx. These are native <form action={…}> elements bound to useActionState(suggestPaths) and useActionState(createPath). No fetch code.

Request

Server action POST with FormData. Route A step 1 sends interest. createPath receives title, goal, depth and useAi. The suggestion's why is shown on the card but never submitted.

Guards

requireStudent(), then hasBloomAiConsent(), which checks for an unrevoked consents row of type bloom_ai. createPath checks consent only when useAi is on.

Context collection

aiContext() (actions.ts L32–36) runs loadStudentOverview and loadBloomPaths in parallel, then bloomContext().

Prompt

Hard-coded template in suggestBloomPaths (ai.ts L136–146) or planBloomPath (L166–180), with context inserted as JSON.stringify(context, null, 2). The system prompt is BLOOM_SYSTEM.

AI call

structured() (ai.ts L98–119) calls client.beta.messages.parse with model claude-opus-5-5, max_tokens: 8000, effort: "low", format: betaZodOutputFormat(schema), beta server-side-fallback-2026-07-01 and fallbacks: "default". There is one user message and no history.

Response and parsing

The SDK returns parsed_output, validated against the Zod schema. A refusal maps to refused, a missing parse to failed, HTTP 429 to rateLimited, and any other error to failed (logged with console.error). There are no retries.

Database

One insert into bloom_paths, then a separate bulk insert of up to 10 bloom_tasks with position = 1..n and default status todo. The two inserts are not in a transaction.

UI

redirect('/student/bloom/{id}') renders StudentPathPage, then BloomPathDetail.

05Existing prompts, verbatim

All prompts are hard-coded template strings in apps/web/src/lib/ai.ts. None are stored in the database, config files or environment variables. There is no separate reflection, follow-up or "regenerate or change path" prompt. Confirmed

5.1 System prompt BLOOM_SYSTEM (shared by all three Bloom calls)

apps/web/src/lib/ai.ts L90–94

You are Bloom, the learning guide inside Youth Idea Lab, an 8-week live online course where students aged 12-18 explore, choose a real problem, build a project and present it at Demo Day. Explorers are 12-14, Builders are 15-18.

You help one student learn what they need for their own project and curiosity. Match the student's age group: short sentences and concrete everyday examples for Explorers; more depth and real tools for Builders. Be warm, encouraging and practical. Prefer doing over reading: small tasks the student can finish in 15-45 minutes with free tools, pen and paper or a phone.

Safety: keep everything age-appropriate. Never ask for or include personal data, contact details, or links to sign-up sites. Never suggest meeting strangers, sharing personal information online, spending money, or anything dangerous. If a question is about wellbeing, safety or something a trusted adult should handle, kindly suggest talking to their parent or mentor.

No variables are inserted.

07Step lifecycle

Example: "Ask your uncle 5 simple questions", a do task at position 2 in the example path. Its stored content couldn't be read (see section 12). The lifecycle below applies to every task. Confirmed from code.

stateDiagram-v2
  [*] --> todo: created (AI plan or Add your own step)
  todo --> doing: Start
  todo --> done: Mark done
  doing --> done: Mark done
  done --> doing: Reopen
  note right of done
    completed_at stamped by trigger.
    If all tasks are done, the path becomes completed
    (unless archived).
  end note
  1. Generation: one element of PlanSchema.tasks from planBloomPath, inserted by createPath (L90–102).
  2. Fields: id, path_id, student_id, position, kind, title, details, status=todo, reflection=null, completed_at=null and timestamps.
  3. Rendering (BloomPathDetail, components/bloom.tsx L91–127): a number circle (a check mark when done), a kind badge, a status badge and the title. A "How to do it" <details> shows the details text and is open unless the task is done. Then come any Q&A for this task, then TaskControls, then an "Ask Bloom about this step" toggle (only with consent and AI configured).
  4. Start: posts status=doing to updateTask. The task updates (.eq("student_id") plus RLS), sibling statuses are re-read and the path status recomputed, then refresh().
  5. Mark done: posts status=done and the optional reflection textarea, which is visible only for reflect tasks or after "Add a note". The result message is "taskDone", or "pathDone" when it was the last task.
  6. Evidence required: none. The reflect textarea is not required.
  7. AI checks: none.
  8. Answer or submission required: none. Answers to the uncle's questions can only go into the free-text note.
  9. Mentor involvement: none in the transition. A mentor can later read the path and leave one note on it.
  10. Stored: status, reflection (or null), completed_at (trigger) and updated_at. The path's status and completed_at may also change, and an audit row is written.
  11. Percentage: recomputed when the page reloads, as done ÷ total. Each task carries equal weight.

Path status machine: active ⇄ completed is automatic, driven only by updateTask. archived is set and cleared manually through setPathStatus (Archive and Restore buttons). Restore always sets active, even if every task is done. Delete removes the path, cascading to its tasks and questions, after a browser confirm(). The backend setPathStatus also accepts completed, but the UI never sends it. Confirmed

08Ask Bloom flow

Click

"Ask Bloom about this step" opens a compact AskForm under the task with a hidden taskId. A general form also sits at the bottom of the page without a taskId.

Action

askQuestion (actions.ts L182–208) checks the student role, a non-empty question (max 1000 characters) and bloom_ai consent.

Context

In parallel it loads the path's title with its tasks' id, title, details, and runs aiContext(). It then finds the task by id within the path; an unknown id is treated as a general question.

LLM

askBloom() makes one call to beta.messages.create with the system prompt from 5.4 and returns plain text.

Persist and render

Inserts into bloom_questions (question, answer, task_id), then refresh(). QuestionList shows the pair under the task or in the general section, and it is visible to parents, mentors and admins.

09"Add your own step" flow

  • Who creates it: the student, entirely manually (AddTaskForm to addTask, actions.ts L107–127). No AI is involved.
  • Fields: title is required (≤160 characters). kind comes from a select of learn, do or reflect, defaulting to do; oneOf() enforces it in code and a Postgres enum in the database. details is optional (≤6000 characters).
  • Persistence: insert with position = count(tasks in path) + 1. Ownership comes from the trigger that copies student_id from the path, plus the RLS check student_id = auth.uid(); the action itself doesn't verify the path.
  • Origin: indistinguishable from AI tasks in the database. There is no per-task origin flag, and ai_generated is per path.
  • Does Bloom know about it? Only when the student asks Bloom about that specific task. Suggestion and plan calls see path titles only.
  • Progress: counts exactly like any other task. However addTask doesn't recompute the path status, so adding a step to a completed path leaves it completed with an open task until another task is updated. Confirmed
  • Editing and deleting steps: no UI or action exists, although column grants and an RLS delete policy would allow it. The UI copy "you can add or change steps later" (bloom.letBloomPlan) promises more than the UI offers.

11Learning-path and course hierarchy

What a path represents: option E, a combination. It is a short, student-chosen learning pathway (C), written by AI as a flat task list (D), sometimes nudged toward project work. It is not a traditional course (A): there are no lessons or content beyond the task text. It is not a project plan (B) either: there are no milestones, deliverables or dependencies, and no link to the project. Inferred from the schema and prompts.

Organization
└── Program (8 weeks)                         programs
    └── Stage: explore · choose · build · present  stages (week_from..week_to)
        └── Activity (per week, per age group)     activities → submissions → feedback

Student, within a Cohort (an instance of a Program)
├── Project (1 per cohort)                     projects
└── Bloom path (many, any time)                bloom_paths   ← tagged with cohort_id + stage_key only
    └── Task (flat, ordered)                   bloom_tasks
        └── Question and answer                bloom_questions
  • What causes a new path: only a student click (section 3). Nothing is automatic or scheduled.
  • Does Bloom know the 8-week journey? Only as the one-sentence description in BLOOM_SYSTEM plus the current step name and week.
  • Does it plan all 8 weeks? No. It plans one standalone path of 3, 5 or 7 tasks per request.
  • Do later paths depend on earlier work? Only to the extent that earlier titles are listed to avoid repeats. There are no prerequisites or ordering between paths.
  • Explicit final deliverable: none in the data model. "Demo Day" appears in the prompt, and "portfolio page" appears only in the seed stage summary, which isn't sent.
  • How Bloom decides what's next: it doesn't. The student home "Continue" card is deterministic: the most recently created active path, and its first not-done task by position (app/student/page.tsx L27–28).

Code behaviour where the frontend and backend differ, or logic conflicts Confirmed by reading; not reproduced

  • A note can be wiped. updateTask always writes reflection: reflection || null. For a reopened non-reflect task, the textarea is hidden until "Add a note" is clicked. Clicking "Mark done" then sends no reflection and clears the saved note.
  • Path and tasks are inserted separately. If the task insert fails, the path is kept with no tasks and only a server log entry.
  • Counts and lengths aren't enforced. Task count, suggestion count and length limits are prompt hints, not schema rules. Up to 10 tasks are accepted regardless of the chosen depth.
  • An inferred goal is discarded. When the goal is blank the model is told to infer one, but there is no field to return it in.
  • The suggestion's why is shown and then lost. It isn't saved or passed to the plan call.
  • Path status can go stale. addTask doesn't recompute it, so a completed path can hold open tasks. Restoring an archived path always sets active, even when every task is done.
  • The backend accepts more than the UI sends. setPathStatus accepts completed with no task check. updateTask accepts any status from any state, including todo.
  • Unused permissions. Task title, details and position update grants and the task delete policy exist with no UI, and the UI copy says steps can be changed later.
  • Totals disagree. Bloom home "overall %" and the mentor group totals (loadBloomTotals) count tasks of archived paths, while the mentor path count excludes archived paths.
  • previousPaths includes archived paths and, in Ask Bloom, the current path itself.
  • Week before the start. Before the cohort starts (week 0), the context reports week 1 and Explore, and stage_key is saved as explore.
  • No limits on archived paths. Ask Bloom and task updates work on archived paths.
  • Duplicate positions are possible. position for added tasks is count+1 and not unique, so concurrent adds can collide.
  • ai_generated is ambiguous. It marks AI-planned tasks, not AI-written titles or goals, and per-task origin isn't recorded.

Dead code, duplicates, unused fields

  • askBloom and draftProgressCard repeat the same create, refusal, text-join and error-mapping logic instead of sharing structured(). This is a duplication note, not a defect.
  • The tasks loaded in askQuestion (all bloom_tasks with details) are used only to find one task; the rest are discarded.
  • The loadStudentOverview fields used by Bloom are a small subset: activities, submissions, sessions and stats are loaded and then ignored for AI context.
  • No unused Bloom columns were found. Every column is written or read somewhere.
