Learn · data model

Organizations, programmes, cohorts and roles

The schema separates the template (what the course is) from the instance (a group of real people taking it). The first migration says so in its header comment.

organizations                 who runs the course (one row today: Youth Idea Lab)
├── programs   (template)     "8-week course", weeks = 8
│   └── stages                Explore 1–2 · Choose 3–4 · Build 5–6 · Present 7–8
│       └── activities        weekly tasks, per age group (null = both)
└── cohorts    (instance)     "Group 1", start_date, timezone, schedule
    ├── memberships           user + cohort_role (student | mentor) + age_group
    ├── sessions              live classes
    └── per student: projects (1 per cohort) · submissions → feedback · progress_cards · bloom_paths

profiles.role (app_role)      student | parent | mentor | admin   (one global role per account)
guardian_links                parent ↔ student
consents                      parent grants per student: platform, ai, bloom_ai, media, public_portfolio

How access works. Every table has row-level security (RLS): Postgres itself filters rows for the signed-in user. Small helper functions answer one question each, and policies combine them:

  • is_admin(): the account's role is admin.
  • is_cohort_member(c) / is_cohort_mentor(c): the user belongs to, or mentors, cohort c.
  • is_parent_of(s): there is a guardian link.
  • mentors_student(s): the user mentors a cohort that student s is in.
  • can_view_student(s): self, or parent, or mentor, or admin. Bloom uses this one.

The organization caveat. organization_id is stored on profiles, programs, cohorts and invitations, but no policy uses it. is_admin() doesn't check the organization, so an admin can see every organization's data, and any signed-in user can read the organizations list. In practice the platform is single-tenant. That's fine for one organization; before a second partner organization is onboarded, admin rights must be scoped to an organization. Bloom v2 doesn't depend on this. New tables reach the organization through the student, so they need no organization_id of their own.

Learn

Why a gateway before features

Today each AI function builds its own client and handles errors itself, and nothing is recorded. With a single gateway, consent, limits, model choice and logging happen in one place. Every later capability (assessor, coach, memory proposer) gets them for free, and we can answer "what does Bloom cost per student?" from ai_runs. The input hash lets us spot repeated calls without storing what children wrote.

Learn

Expand, migrate, contract

Changing a live schema safely happens in three moves. Expand: add new columns and tables beside the old ones, keeping them in sync (1.1). Migrate: move the code and the data over gradually (1.5–1.8, and later phases). Contract: remove the old parts only once nothing uses them (phase 6). At every point the app works, and a bad deploy can roll back without data loss. Postgres enums are a good example: you can add values but not easily remove them, so the plan adds a new state column instead of reshaping status.

Why the state machine is a pure function

transition(current, event) → next has no database or network inside it, so every rule can be unit tested in milliseconds. The database step then writes with a guard (where state = 'in_progress'). If two requests race, only the first matches, which is called optimistic concurrency.

Learn

Evals: testing AI like any other function

Unit tests can't tell you whether feedback is good. An eval is a fixed set of inputs with expected judgements, made by a human expert. You run it whenever a prompt, rubric or model changes, and compare the agreement number. Keep the set in the repo (anonymised and invented, never real student work) and treat a drop in agreement like a failing test.

Fail-open versus fail-closed

When a check can't run, you either allow (fail-open) or block (fail-closed). Bloom's learning checks fail open, because a child shouldn't be stuck when an API is down; the mentor sees the "not reviewed" flag. Safety and permission checks fail closed: no consent means no AI call, and a failed PII check means no submission.

Learn

How file security works here

Supabase Storage applies RLS policies to file paths too. The existing course uploads use <cohort_id>/<student_id>/<file> (lib/storage.ts), and the storage policies parse that path to decide access. Files are never public. The app creates signed URLs that expire after 10 minutes. Bloom evidence follows the same pattern with its own bucket, so its rules can differ (drafts stay private).

Evidence versus artifacts

A submission answers "did the student do this activity?". An artifact version answers "what does the project have now?". Keeping them separate means a quiz never clutters the project, and an artifact can later be fed by course submissions too.

Learn

The propose-and-confirm pattern

Language models are good at noticing and phrasing, and unreliable as a source of truth. So AI output goes into a proposed state, and a person's click promotes it. Because changes create new rows that point to the old ones (supersede) instead of overwriting them, you can always answer "what did we believe in week 3, and why?". The same idea is behind the immutable artifact versions.

Why the brief is compiled, not generated

If an LLM summarised the project, the summary could drift or invent details, and you couldn't reproduce it. Compiling it from rows with code gives the same output for the same data, makes it testable, and costs nothing.

Learn

Context windows and budgets

Each AI call can only "see" what's in its prompt. If you append every message forever, prompts grow, get slower and costlier, and models pay less attention to what matters. Fixed slices with budgets (project brief, this activity, recent messages) keep calls predictable. A rolling summary of older messages comes later (phase 2 of the blueprint).

Why mentor review is an RPC

Students must never move their own work out of "awaiting mentor". Granting mentors general update rights on student tables would be too broad. A security-definer function runs with elevated rights but checks mentors_student() first and changes exactly one thing, like the existing set_bloom_mentor_note.
