Youth Idea Lab · Bloom, phase 2 design proposal

Bloom as a project-learning coach: target architecture

How Bloom evolves from an AI-written checklist into a coach that helps each student make real things for their project, get feedback and improve them. It builds on the existing tables, actions and pages instead of replacing them.

Status proposal for review, nothing implemented Baseline Bloom as built (docs/bloom-as-built) Written 5 Oct 2026
MVP phase 1, needed to make Bloom interactive Phase 2 once the core works Later advanced

00Summary and key decisions

AI recommends and interprets. The application decides and stores the truth. Every meaningful path ends with something new on the student's project.

  1. Keep the tables and evolve them. bloom_paths stays the path. bloom_tasks becomes the activity table, gaining a type, a config and a richer state. The existing kind (learn, do, reflect) is kept as the path's three phases.
  2. A short, fixed catalogue of 8 activity types, each defined in code with its own evidence spec, completion rule and optional rubric. The AI planner can only assemble activities from this catalogue; it never invents new types.
  3. Work is submitted, not ticked off. Doing an activity creates a submission with evidence. Simple types complete instantly. Types that produce something get an immediate AI rubric review, which gives advice but caps revision requests at 2. Mentors review only at milestones.
  4. Artifacts and project memory belong to the project, not the path. An accepted submission can create a new artifact version. AI can propose project facts, but only a student or mentor confirmation writes them.
  5. AI is a set of narrow, typed functions (planner, coach, assessor, memory proposer, brief writer). They share one context assembler and one AI gateway that handles consent, limits and logging. It is not an autonomous agent: AI has no tools that write data.
  6. The spine is the existing programme stages. Each stage (Explore, Choose, Build, Present) lists the artifacts it expects. "What's next" is a deterministic gap check against that list, and the planner then fills in the detail.

01Student experience, end to end

Example: an Explorer (age 13) in week 3 (Choose stage). Project area is business; working idea: "a logo and a brand for my uncle's shop".

Opens Bloom

The home page leads with "Your project": a project card showing the current stage (Choose), what the stage expects (problem statement, at least 2 interviews), and what already exists (none yet). Below it is "Recommended next": 1–3 paths picked because something is missing, for example "How a small business really works → produces a Business Map and an Interview". The curious-about field and "my own topic" stay as before.

Chooses a path

The student taps "Start". The planner builds the path from the catalogue: 5 activities in 3 phases, aimed at Business Map as the target artifact. The path page shows that target at the top: "By the end you'll have: a money map of your uncle's shop."

Starts a step and learns

Activity 1 is a Learn activity: 3 short cards on customers, what's sold and money in or out, with examples from a corner shop. There's an optional "I already know this, check me" link. A Quick check follows: sort 6 items ("rent", "selling sweets", "neighbours walking past", …) into the 3 parts. 5/6 correct completes it. A wrong answer gets a one-line hint and one retry.

Talks to Bloom

In any activity, "Ask Bloom" opens a thread for that activity. Bloom knows the project, the path, this activity and what the student has typed so far. Example: "What should I ask if my uncle is busy?" gets a short answer and a suggestion to pick the 3 most important questions.

Does a real task

Activity 2 is an Interview. The student chooses 5 questions from suggestions or writes their own, and Bloom flags any closed (yes or no) ones. The student talks to their uncle offline, then records an answer under each question, saying who was interviewed by role ("my uncle, the shop owner"), never by name. They can add a photo of their handwritten notes.

Submits work

"Submit" runs deterministic checks first: 5 answers, each at least a few words, nothing that looks like a phone number or address. Then comes an AI rubric review that takes a few seconds and is shown inline.

Gets feedback

"Great detail on how customers find the shop. Answer 4 ('money is ok') is short. Can you ask your uncle which costs are biggest?" Each criterion is marked met or not yet. The verdict is needs revision because one required criterion isn't met.

Revises

The student adds "rent and buying stock are the biggest costs" and resubmits. The revision is accepted. After at most 2 revision requests, the work is always accepted, with a note for the mentor.

Completes the activity

The activity becomes complete. The app creates Interview: uncle's shop, v1 as a project artifact.

Project memory updates

Bloom proposes up to 3 facts: "Most customers are neighbours who walk past", "Biggest costs are rent and stock", "Open question: do customers know the shop's name?". The student keeps, edits or dismisses each. Only kept facts are saved, as confirmed and attributed to this submission.

Next becomes relevant

Activity 3 (Make: Business Map) is pre-filled from those facts. After the path ends with a Decide ("where would a logo help most?") and a Reflect, the gap check now shows "Choose stage: interviews 1 of 2, problem statement missing". The next recommendation is "Ask 3 customers what they notice about the shop", which feeds the problem statement. The mentor's next session brief mentions the new Business Map.

03Path structure

Decision: evolve, don't replace. Learn, Do, Reflect is already in the data (kind) and students understand it. It becomes the path's three phases, while the new type says what each activity actually is. Feedback and improvement aren't separate steps: they are the review loop inside each Do activity.

Phase (existing kind)Shown asActivity typesRule
learnUnderstandLearn, Quick check1–2 activities, test-out allowed
doMakeRespond, Interview, Make, TryAt least one activity that produces evidence. Each one runs submit, then feedback, then improve. Exactly one is the path's core make, which produces the target artifact.
reflectDecide & reflectDecide, Reflect, Mentor checkEnds the path. A Decide activity writes a project decision; a Reflect activity records learning.

Two path shapes:

  • Project path (the default for recommendations): it has a target_artifact_type, and its core make activity creates or improves that artifact. 4–6 activities.
  • Curiosity path (when the student's own topic has no project link): Understand, a short Respond or Try, then Reflect. It needs no artifact and keeps the open-ended curiosity Bloom has today. 3–4 activities.

The depth setting (quick, standard, deep) is replaced by the shape plus a size rule. A path the student marks "deep dive" may add a second Do activity.

  • Validation runs in four layers: (1) the evidence spec, deterministic, which blocks submit; (2) safety: PII patterns and, later, image moderation, which blocks with an explanation or flags; (3) the AI rubric, which is advisory and can ask for a revision; (4) a mentor, only at milestones.
  • Honesty about offline work: the app can't prove an interview happened. Evidence is good faith, made more credible by specific answers and the optional photo of notes. Mentors spot-check during sessions. Bloom never accuses a student of making work up.
  • Visibility: same as Bloom today (can_view_student). Drafts are visible only to the student; submitted work is visible to the mentor and parent.

05Completion and state machine

stateDiagram-v2
  [*] --> available
  available --> in_progress: first edit or draft saved
  available --> skipped: test-out passed / optional skipped
  in_progress --> submitted: Submit (spec checks pass)
  submitted --> complete: instant types (Learn, Quick check, Decide, Reflect)
  submitted --> needs_revision: AI review says not yet (max 2 times)
  submitted --> awaiting_mentor: accepted + activity is a milestone
  submitted --> complete: AI review accepted
  needs_revision --> submitted: Resubmit
  needs_revision --> awaiting_mentor: Keep as is (milestone)
  needs_revision --> complete: Keep as is (non-milestone, flagged for mentor)
  awaiting_mentor --> complete: mentor approves
  awaiting_mentor --> needs_revision: mentor asks for changes
  complete --> in_progress: student reopens to improve (new attempt)
  • AI review is not a state the student waits in. It runs inside the submit request (a few seconds, with a visible progress state) and is stored as an assessment. If the AI fails or times out, the work is accepted and flagged "not reviewed" for the mentor. AI problems never block a student.
  • Revision cap: at most 2 AI-requested revisions per activity. After that the work is accepted with an "AI still had suggestions" note. "Keep as is" is always available, and it sends the work to the mentor queue without blocking.
  • Mentor review never blocks the rest of the path. The student can carry on; only the milestone itself stays pending. A path completes when all required activities are complete or awaiting a mentor; optional activities don't count.
  • Path state stays active, completed or archived, and is now recomputed in one place (a database function or service) after every activity change. That fixes the stale-status bugs found in the as-built analysis.
  • Mapping existing data: todo becomes available, doing becomes in_progress, done becomes complete.

06AI responsibilities

Decision: separate typed functions behind one gateway, not a single orchestrating agent. Each capability has its own prompt, input type, Zod output schema and tests. What they share:

  • Context assembler (deterministic): builds the right slices of project memory and activity data for each capability, within a token budget.
  • AI gateway: checks consent, limits per student, picks the model per capability, records every call in ai_runs (capability, model, tokens, latency, outcome, input hash), and turns failures into safe fallbacks. This replaces the scattered calls in today's lib/ai.ts.

A single agent with tools would make the app's state depend on model behaviour, which is exactly what this design avoids.

10Adaptive learning

  • The spine is a milestone map in code, keyed by stage. It lists the artifacts each stage expects: Explore (an interest or exploration note, 1 interview), Choose (2+ interviews, a problem statement checked by the mentor), Build (a concept, a prototype checked by the mentor, 1 experiment), Present (a pitch checked by the mentor, a portfolio). The gap check compares it with the project's artifacts. That deterministic list drives "Recommended next".
  • No repetition: if the target artifact already has a current version, the planner is told to make an "improve" path (v2), not a new "create" path. The planner also receives the titles, targets and outcomes of the last 12 paths.
  • Skip what's known: Learn activities offer a test-out quick check. Passing it marks Learn as skipped and records skill evidence (P2).
  • Micro-lessons when needed: wrong quick-check answers, or a "not yet" on a concept criterion, trigger an inline Coach explanation inside the activity. It isn't a new activity, so the path doesn't grow.
  • Reference earlier work: activity configs can reference artifacts and facts by id (for example, the Business Map is pre-filled from interview facts), and the brief includes artifact summaries.
  • Gaps across paths P2: criteria the student repeatedly misses (such as "answers lack specifics") feed the planner as "practise: …".

11Ask Bloom

There is one thread per activity plus one general thread per path, with messages kept as rows. The existing bloom_questions become messages in these threads. Context is assembled by scope with fixed budgets, so prompts don't grow with use:

  • Growth control: scoped threads, truncation by recency, and a rolling summary rebuilt every 8 messages by a cheap call P2. The MVP uses the last 8 messages only. Search across threads (vector retrieval) is Later and only if needed.
  • Limits: the Coach can suggest an action ("Add a step: ask two customers") that appears as a button. Only the student's click acts on it. It can't complete work or reveal answer keys.
  • Safety: wellbeing or safety topics get the existing "talk to a trusted adult" handling plus a mentor and admin flag MVP.

12Mentor role

  • Checkpoints at milestones only: problem statement (Choose), prototype (Build) and pitch (Present) MVP for the problem statement, P2 for the rest. Decisions marked as milestones, such as "my chosen problem", are also checked.
  • The mentor queue (one list per group, sorted by urgency): awaiting mentor; "kept as is" and "not reviewed" items; students stuck (2 revisions in a row, or no activity for 5+ days, reusing loadLastActive); safety flags.
  • Per-student view: the project brief, the artifact timeline with versions, paths and progress, recent assessments, and the existing timeline.
  • Mentor actions: approve or ask for changes (with a comment), confirm, edit or retire a project fact, and the existing per-path note.
  • Mentor brief P2: before each live session, a per-student card covering what they made since last time, where they got stuck, the topics they asked Bloom about, open milestones, and 1–2 suggested talking points. Every point links to its source.

16MVP vs later

MVP / phase 1

  • Activity types: Learn, Quick check (choice, sort), Respond, Interview, Make (template, photo, file), Decide, Reflect, Mentor check
  • Submissions, evidence spec checks, image and file upload with EXIF stripping, PII patterns
  • AI Assessor with rubrics, revision loop (cap 2), fail-open behaviour
  • New state machine and transactional path creation
  • Artifacts and versions: interview set, business map, problem statement, generic image or file
  • Project facts with propose and confirm; the compiled brief
  • Planner using the catalogue, the brief and the gap check (milestone map)
  • Ask Bloom threads per activity, with the last 8 messages
  • Mentor queue plus one checkpoint (problem statement)
  • AI gateway: consent, daily limit, ai_runs log
  • Legacy path support

Phase 2

  • Mentor brief before sessions
  • Skill evidence and the skill view
  • Test-out on Learn; cross-path gap patterns
  • Recommender ranking; rolling thread summaries
  • Customer profile, prototype, experiment and pitch artifacts; prototype and pitch checkpoints
  • Parent artifact view; portfolio from final versions
  • Course submissions feeding artifacts

Later

  • Drawing canvas, voice evidence with transcription
  • Image moderation service; peer review

  • Analytics on learning outcomes across cohorts
